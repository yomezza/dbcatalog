# Структура и оптимизация CatalogDB 0.9.0

## Серверный backend 0.9.0

Основные операции над данными теперь находятся в SQL API выбранной схемы: api_save_record, api_catalog_page/matches, api_move_preview/object, api_delete_records, api_restore_records, api_apply_staged_writes, api_bulk_update, api_statistics, api_lookups, api_quality_issues.

Go сохраняет авторизацию/жизненный цикл сессии, обработку файлов и подтверждений, подготовку импорта и вызовы транзакций. Авторизация проверяет роль, состояние и сохранённую сессию одним запросом с блокировкой пользователя. PostgreSQL обслуживает технические версии, историю/аудит, перемещения и уведомления. Транзакционный контекст передаётся через SET LOCAL; это не самостоятельный механизм удостоверения личности при прямом доступе с общими реквизитами БД.

live.go держит отдельное соединение LISTEN в существующем процессе; при потере связи переподписывается и посылает resync. useLiveUpdates объединяет события, откладывает работу при foreground-операциях/скрытом окне, ограничивает повторные попытки и отбрасывает ответы старой сессии. Формы не перезаписываются.

Миграции 010–016, точный состав секций, история без дублирования JSON, сохранение входа и ограничения: [postgresql-backend-0.9.0.md](postgresql-backend-0.9.0.md). Ниже сохранено описание предшествующей оптимизации; замечания про схему 009 относятся к 0.8.0.

## Границы модулей

- app.go и desktop*.go: тонкий Wails bridge, нативные диалоги/клиенты Windows.
- internal/application: сценарии приложения, авторизация, транзакции, каталог, импорт, история, архив удалений.
- internal/database: PostgreSQL, встроенные миграции и их контрольные суммы.
- internal/config, security, spreadsheet, downloads: настройки, пароли, чтение/запись Excel и локальные файлы.
- frontend/src/main.tsx: запуск React.
- frontend/src/App.tsx: сессия, маршрутизация разделов, координация действий и окон.
- frontend/src/features/catalog: каталог, фильтры, массовая правка, узел дерева и состояние просмотра.
- frontend/src/features/quality и features/deleted: самостоятельные разделы качества/восстановления.
- frontend/src/catalog: чистые алгоритмы поиска, фильтрации, индексов и навигации.
- frontend/src/ui: общие типы действий и постраничная навигация.

Основные направления зависимостей:

~~~mermaid
flowchart LR
    UI["React: App и разделы"] --> Bridge["Wails: App"]
    Bridge --> Service["application: авторизация и транзакция"]
    Service --> Reads["loadCatalog / loadLookups / loadFavorites / loadPolicies"]
    Service --> Writer["catalogWriter: проверка и запись"]
    Reads --> PG["PostgreSQL"]
    Writer --> PG
    UI --> Algorithms["catalog: поиск и индексы"]
~~~

## Что изменено и зачем

### Импорт и проверка справочников

Ранее проверка каждого значения выполняла SELECT EXISTS. На синтетическом наборе 600 строк проверка плана вызывала 5400 запросов к lookup_values.

Теперь choiceSet загружается одной выборкой и переиспользуется при проверке пакета. Это снимок одной операции/транзакции, а не глобальный кеш. Подтверждение импорта и массовой правки заново читает справочники и проверяет актуальные права. Смена справочника между предпросмотром и сохранением не обходит валидацию.

catalogWriter объединяет транзакцию, сервис и этот снимок. Создание/обновление, возврат к версии и восстановление удалённого объекта используют одну реализацию записи. Именованные режимы заменяют пары булевых аргументов.

Атрибуты при слиянии строк Excel объединяются типизированным кодом вместо JSON → map → JSON. Пустые ячейки по-прежнему сохраняют прежние значения; массив работы АБД копируется, не разделяя память с исходным объектом.

### Загрузка рабочего экрана

Основной экран вызывает GetCatalogWorkspace: первая страница серверов, общие счётчики, справочники и избранное читаются в одной авторизованной транзакции REPEATABLE READ. Полный каталог и все политики в клиент не передаются.

BrowseCatalog загружает страницы по раскрытию ветвей. Общий SQL-предикат используется для поиска, фильтров, счётчиков, глобального выделения, выбора родителей и экспорта. GetObjectContext возвращает только объект, предков, связанные политики и номера страниц для перехода. GetPolicyPage отдельно загружает политики по 25 строк.

Совместимые GetWorkspace/GetCatalog/ListPolicies сохранены для прежних вызовов; новый интерфейс их для загрузки разделов не использует.

### Сохранение

Раньше основные поля объекта сохранялись первым запросом, а атрибуты/среда — следующим UPDATE. Теперь основной INSERT или UPDATE включает все поля и новую версию сразу. Чтение прежней версии с блокировкой, история, аудит, уведомления и атомарность остаются отдельными обязательными частями операции.

### Интерфейс

useCatalogBrowser управляет страницами и кешем текущего просмотра; ответы устаревшего поиска отбрасываются. RemoteCatalogTree выводит только видимые строки с небольшим запасом. Разворачивание загружает ветви по мере появления в области просмотра. ObjectPicker ищет родителей глобально по 25 записей.

Подсчёт скрытого выделения и выбор всего результата выполняются в PostgreSQL. Переходы из избранного, качества и уведомлений получают актуальный контекст и открывают нужные страницы. Сохранение обновляет карточку и сбрасывает устаревшие выделенные версии.

features/documents и features/movements содержат отдельные диалоги. internal/documents формирует DOCX без стороннего генератора; application/attachments.go управляет файлами и правами, movements.go — предпросмотром, подтверждением и историей переносов.

TypeScript теперь проверяет неиспользуемые импорты, переменные и параметры при обычной сборке.

## Измерение

Одинаковый BenchmarkImportPlan600, PostgreSQL 17 в локальной облачной среде, 3 измеряемые итерации, без race detector:

| Построение плана для 600 строк | До | После |
| --- | ---: | ---: |
| Время | 784,4 мс | 5,5 мс |
| Запросы к справочникам | 5400 | 1 |
| Выделено памяти на операцию | 5,18 МБ | 2,94 МБ |
| Выделений памяти | 58396 | 4606 |

Измеряется проверка уже разобранной книги при пустом каталоге, без чтения XLS/XLSX и сохранения записей. Это не оценка ускорения всего импорта или приложения; время на рабочем сервере зависит от данных и задержки сети.

Воспроизведение:

~~~bash
CATALOGDB_TEST_DATABASE_URL='postgres://catalogdb:catalogdb-test-only@127.0.0.1:55432/catalogdb_test?sslmode=disable' go test ./internal/application -run '^$' -bench BenchmarkImportPlan600 -benchtime=3x -count=1
~~~

Тест создаёт и удаляет случайную схему. Используйте отдельную тестовую PostgreSQL.

## Совместимость и оставшиеся границы

Миграция 009 добавляет вложения, историю перемещений, вычисляемые поисковые поля и индексы сортировки. Контрольные суммы миграций 001–008 не меняются. Старый клиент не должен работать с более новой схемой: проверка журнала миграций блокирует несовместимую версию.

Сервис сохраняет mutex сессии. Пагинация и виртуализация ограничивают данные клиента, но глобальный поиск произвольной подстроки и счётчики требуют обработки подходящих записей PostgreSQL. Это не обещание постоянного времени поиска при любом объёме; отдельный сервер БД и реальные данные требуют измерений. Поиск не ограничен текущей страницей.

Проверки Windows остаются отдельным этапом: успешная кросс-сборка не подтверждает нативные диалоги, Credential Manager и RDP/SSH.
