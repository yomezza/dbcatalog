# Известные ограничения и незавершённые решения

Состояние на 23 октября 2026 года, приложение 0.12.0. Этот список передаёт результаты предыдущих проверок и обсуждений, **не разрешает автоматически выполнять перечисленные изменения**. Перед исправлением сверяйте актуальный код и задачу пользователя.

## Безопасность и граница прямого SQL-доступа

### Общие широкие реквизиты PostgreSQL

`internal/application/service.go` использует реквизиты подключения и для миграций/обслуживания секций, и для обычного пула. Прикладные роли проверяются сервисом; SQL-функция `catalog_actor` в миграции 012 доверяет `catalogdb.actor_id`, задаваемому клиентом.

При наличии общих PostgreSQL-реквизитов с широкими правами прямой SQL-клиент может обойти прикладные ограничения, прочитать доступные ему хеши пользователей, менять таблицы и подставлять автора. Это подтверждалось на отдельной синтетической схеме с откатом. Возможность указать имя сервера/базы сама по себе не является уязвимостью; проблема — полномочия общего подключения и доверие клиентскому actor.

Не обещайте изоляцию от недоверенных пользователей только за счёт кнопок и ролей UI. Владельца схемы/суперпользователя также нельзя изолировать от его собственных данных обычными прикладными проверками.

Обсуждавшееся направление — персональные PostgreSQL-логины, доверенная идентичность `session_user`, защищённое сопоставление с UUID профилей и отдельная учётка миграций. **Пользователь просил пока не внедрять.** Подробности и статус — в [контексте](../PROJECT_CONTEXT.md#обсуждалось-но-не-реализовано).

### Сеансы и подбор пароля

- В `service.go` задержка между входами локальна одному процессу (1 секунда). Это не общая серверная защита от перебора несколькими клиентами.
- Миграция 014 отзывает сохранённые сессии после смены пароля или отключения пользователя. Обычный открытый сеанс без сохранённого токена от одной смены пароля может продолжать работать.
- Состояние и роль перечитываются при операциях; блокировка учётной записи запрещает дальнейшие авторизованные операции. Это не означает очистку уже показанных на экране данных.
- При будущей PostgreSQL-аутентификации смена пароля и `VALID UNTIL` сами по себе также не завершают все существующие соединения. Сохранение входа на часы требует отдельного проектирования.

### Зависимости и пределы аудита

Предыдущая проверка npm 23 октября 2026 года сообщила о **8 затронутых пакетах инструментов разработки** (2 critical, 3 high, 1 moderate, 2 low); production-дерево frontend по тому аудиту — 0 известных проблем. Среди требовавших внимания версий — Vitest 3.2.4, Playwright 1.55.0 и Vite 6.3.5.

Это не восемь автоматически эксплуатируемых ошибок готового EXE: важны условия запуска dev/test-серверов и загрузки браузеров. Это также не бессрочное заключение безопасности production. Перед отдельной задачей обновления повторите `npm audit`, оцените advisories и выполните проверки после изменения lockfile.

Go vulnerability scan не удалось завершить из-за сетевого запрета доступа к базе advisories. Его результат нельзя описывать как «уязвимостей нет». Проверка `go mod verify` подтверждала соответствие кешированных модулей контрольным суммам, а не отсутствие вредоносного кода.

В просмотренном собственном коде не были обнаружены признаки специального пароля, скрытой отправки данных или скрытого выполнения команд. Найденные запуски внешних программ относились к RDP/SSH и открытию файлов. Это ограниченный обзор исходников, не гарантия для всех зависимостей, системного WebView или поставленных бинарников.

## Производительность и работа нескольких клиентов

Пагинация, виртуализация и серверный глобальный поиск уже есть. Кандидаты дальнейшей оптимизации:

| Наблюдение | Где смотреть / ограничение изменения |
| --- | --- |
| `Service.mu` последовательно обслуживает много операций одного процесса | `internal/application/service.go`; разделять соединение/сессию и долгие операции с проверкой конкурентности |
| Live-refresh сбрасывает выделение БД и может переинициализировать дерево | `frontend/src/App.tsx`, `useCatalogBrowser.ts`; сохранить защиту от устаревших версий и ответов |
| Справочники DISTINCT, качество данных и некоторые счётчики могут обходить большие наборы | SQL API миграций 010/015 и `lookups.go`, `quality.go`; измерять на реальном профиле данных |
| План импорта, Excel и base64 bridge требуют памяти | `import*.go`, `internal/spreadsheet`, `ExcelPanel.tsx`; лимиты уже есть, но это не потоковый импорт |
| Часть массовых операций использует широкие блокировки | Импорт, удаление, восстановление, перемещение; нельзя снимать блокировки, теряя повторную проверку состава |
| SQL-пакет импорта всё ещё вызывает серверную запись по объектам | `api_apply_staged_writes` / `api_save_record`; изменение не должно обходить триггеры и историю |

Предыдущие локальные измерения на синтетике не гарантируют время ответа по сети или на рабочем сервере. Для оптимизации сначала сохраняйте воспроизводимый сценарий и план SQL, затем сравнивайте.

LISTEN/NOTIFY уже работает. Проверяйте состояние в диагностике прежде, чем предлагать реализовать его заново. События могут теряться при отключении; переподключение и resync закрывают этот случай. Открытые формы откладывают обновление, чтобы сохранить ввод пользователя.

## Данные, файлы и резервные копии

- Политика РК — описание, не исполнение задания и не мониторинг фактической копии. Сервис приёма отчётов/PostgREST отложен.
- Архив версий, «Удалённые» и XLSX не заменяют резервную копию всей PostgreSQL с зависимостями и вложениями.
- Общие вложения остаются после удаления объектов; автоматической сборки мусора нет. Они увеличивают объём основной БД и резервных копий.
- Удаление самого вложения физическое. Архив карточек не является историей всех редакций прикреплённых файлов.
- Локальные загрузки нужно сохранять отдельно, если они нужны на другом компьютере. Рабочий исходный Excel автоматически целиком не архивируется.
- Исправленная копия предпросмотра Excel содержит только 21 колонку и может ещё содержать ошибки; настройки политик текущего плана в неё не входят.
- Старые неполные снимки не позволяют восстановить отсутствовавшие данные задним числом; восстановление может показать конфликт.

## Платформы и выпуск

- Настоящая Linux GUI проверена под Debian 13/Xvfb; это не полный прогон каждой Wayland/X11-сессии и каждого дистрибутива.
- Облачные Linux-архивы требуют glibc 2.41+, GTK 3 и WebKitGTK 4.1. Для старой системы нужна подходящая сборка.
- Windows EXE собран. Последняя проверка не подтверждает новый интерактивный прогон установщика, Credential Manager, RDP/SSH и диалогов на Windows.
- Внешние клиенты используют RDP 3389 / SSH 22; нестандартные порты и хранение удалённых паролей пока не предусмотрены.
- **Перед следующим выпуском** нужно выполнить новое правило Release label Latest / None. Старый publisher сохраняет Pre-release и `make_latest: false`; исправлять следует на уровне нового выпуска, без массовой перемаркировки истории. [Подробности](DEVELOPMENT.md#latest--none-обязательное-изменение-перед-следующим-выпуском).
