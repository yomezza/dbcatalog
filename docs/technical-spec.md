# Техническое задание: CatalogDB («Каталог БД») — версия на Go

## 1. Общая информация

**Название проекта:** CatalogDB («Каталог БД»).

**Тип приложения:** настольное корпоративное приложение для Windows.

**Основное назначение:** централизованный учёт, администрирование и инвентаризация серверов, экземпляров СУБД, баз данных, ответственных лиц и политик резервного копирования.

**Целевая аудитория:** администраторы баз данных (DBA), системные администраторы, специалисты сопровождения информационных систем, руководители ИТ-подразделений и сотрудники, которым требуется просматривать инфраструктуру баз данных.

**Язык интерфейса:** русский.

**Основные технологии:**
- Go — основной язык приложения: бизнес-логика, PostgreSQL, авторизация, Excel и интеграции с Windows. Использовать поддерживаемую стабильную версию; точные версии Go и инструментов зафиксировать при создании проекта в `go.mod` и документации сборки.
- Wails v2 — настольная оболочка и взаимодействие интерфейса с Go.
- TypeScript, React и Vite — графический интерфейс внутри Windows WebView2. Это дополнительный язык слоя представления; бизнес-правила реализуются на Go.
- Microsoft Edge WebView2 Runtime — среда отображения интерфейса Windows.
- PostgreSQL — централизованное хранение данных приложения.
- `github.com/jackc/pgx/v5`, включая `pgxpool` — подключение к PostgreSQL и пул соединений.
- Go Modules (`go.mod`, `go.sum`) — управление зависимостями Go; npm с `package-lock.json` и `npm ci` — воспроизводимая установка зависимостей интерфейса.
- `github.com/xuri/excelize/v2` — импорт и экспорт Excel `.xlsx`.
- `github.com/zalando/go-keyring` — доступ к Windows Credential Manager через изолированный адаптер хранения секретов.
- `golang.org/x/crypto/argon2` — Argon2id для хеширования пользовательских паролей.
- Встроенный runner миграций на pgx: последовательные SQL-файлы через `go:embed`, транзакции, advisory lock и SHA-256 применённых файлов.
- Стандартные пакеты Go `testing`, `log/slog`, `context`, `errors` — тестирование, структурированные журналы, отмена операций и обработка ошибок.
- Wails CLI и Go toolchain — сборка Windows EXE.
- Inno Setup — создание установщика Windows.

**Границы выбора стека:** Wails v2 и React выбраны для сохранения требований к собственному оформлению окна и насыщенному табличному интерфейсу. Пользователь запускает настольное приложение; отдельный браузер или сервер интерфейса при эксплуатации не требуется. Node.js нужен для разработки и сборки, но не на компьютере конечного пользователя. Python и его инструменты проекту не требуются.

Приложение должно быть рассчитано на использование несколькими сотрудниками с разных компьютеров. Все пользователи подключаются к одной центральной базе PostgreSQL и видят актуальные данные в соответствии со своими правами.

**Ключевой принцип:** CatalogDB — это не СУБД и не инструмент выполнения SQL-запросов к пользовательским базам. Это каталог инфраструктуры, в котором хранятся сведения об объектах и процессах их сопровождения.

1. Создать единый реестр серверов, экземпляров СУБД и баз данных организации.
2. Исключить разрозненное хранение информации в Excel и других файлах.
3. Предоставить удобную иерархическую навигацию по инфраструктуре.
4. Вести сведения об ответственных администраторах и подразделениях.
5. Учитывать политики резервного копирования на разных уровнях.
6. Сохранять историю изменения объектов.
7. Контролировать действия пользователей.
8. Обеспечить разграничение доступа.
9. Поддерживать импорт существующих реестров Excel и экспорт актуального каталога.

11. Обеспечить удобное развёртывание на Windows через установщик.

## 3. Архитектура инфраструктурного каталога

В системе должна использоваться следующая иерархия:

**Сервер → Экземпляр СУБД → База данных**

### 3.1. Сервер

Сервер представляет физическую машину, виртуальную машину или иной вычислительный узел, на котором размещается одна или несколько СУБД.

Для сервера предусмотреть:
- Уникальный идентификатор.
- Имя сервера / hostname.
- IP-адрес.
- Дополнительные сетевые адреса, если потребуется.
- Операционную систему.
- Назначение сервера.
- Среду эксплуатации (например, промышленная, тестовая, разработка).
- Статус.
- Описание и примечания.
- Ответственных лиц.
- Дату создания записи.
- Дату последнего изменения.
- Пользователя, создавшего или изменившего запись.

Один сервер может содержать несколько экземпляров СУБД.

Нельзя считать, что одинаковый IP-адрес автоматически означает один и тот же сервер: возможны разные сетевые конфигурации, а также ошибки исходных данных. Для поиска дублей нужно использовать явно определённые правила и предупреждать пользователя.

### 3.2. Экземпляр СУБД

Экземпляр СУБД — установленный и работающий экземпляр системы управления базами данных.

Для него предусмотреть:
- Уникальный идентификатор.
- Ссылку на сервер.
- Тип СУБД.
- Версию СУБД.
- Имя экземпляра.
- Порт подключения.
- Статус.
- Назначение.
- Описание.
- Ответственных администраторов.
- Даты создания и изменения.

Поддерживать разные типы СУБД, в частности PostgreSQL, Microsoft SQL Server, Oracle и другие. Список типов должен расширяться через справочник, а не через изменение кода.

**Особенность Oracle:** модель должна учитывать, что логическая структура Oracle может отличаться от PostgreSQL и SQL Server. Нельзя автоматически считать все базы на одном сервере одним экземпляром. Импорт и идентификация объектов должны учитывать реальные границы экземпляров.

### 3.3. База данных

Для каждой базы данных предусмотреть:
- Уникальный идентификатор.
- Ссылку на экземпляр СУБД.
- Название базы данных.
- Назначение / информационную систему.
- Статус.
- Описание.
- Ответственных лиц.
- Дополнительные примечания.
- Даты создания и изменения.
- Сведения об авторе последнего изменения.

Один экземпляр СУБД может содержать несколько баз данных.

Иерархия должна поддерживать ситуации, когда на сервере есть экземпляр СУБД без зарегистрированных баз данных, а также сервер без экземпляров.

## 5. Общий каталог объектов

Это основной рабочий раздел.

### 5.1. Представление данных

Реализовать иерархическое дерево:

- Сервер.
  - Экземпляр СУБД.
    - База данных.

При выборе объекта справа или снизу отображается карточка с подробной информацией.

Должны поддерживаться:
- Раскрытие и сворачивание узлов.
- Поиск по именам, IP-адресам и другим значимым полям.
- Фильтры по типу СУБД, статусу и другим характеристикам.
- Обновление списка.
- Контекстное меню по правой кнопке мыши.
- Открытие карточки объекта.
- Редактирование с учётом прав.
- Добавление дочерних объектов.
- Просмотр истории объекта.
- Добавление объекта в избранное.
- Переход к политикам резервного копирования.

### 5.2. Контекстные действия

Для сервера:
- Открыть карточку.
- Изменить.
- Добавить экземпляр СУБД.
- Просмотреть историю.
- Добавить в избранное.
- Удалить при наличии прав.

Для экземпляра СУБД:
- Открыть карточку.
- Изменить.
- Добавить базу данных.
- **Добавить политику РК**.
- Просмотреть историю.
- Добавить в избранное.
- Удалить при наличии прав.

Для базы данных:
- Открыть карточку.
- Изменить.
- **Добавить политику РК**.
- Просмотреть историю.
- Добавить в избранное.
- Удалить при наличии прав.

Такие действия должны быть доступны не только в общем каталоге, но и в специализированных разделах «Экземпляры СУБД» и «Базы данных».

### 5.3. Пагинация

При большом количестве серверов каталог должен использовать постраничную загрузку.

В предыдущей реализации применялся размер страницы **10 серверов**. Этот размер можно сохранить как значение по умолчанию и сделать настраиваемым.

Важно: при пагинации основная единица страницы — сервер, вместе с принадлежащими ему экземплярами и базами. Нельзя случайно разрывать иерархию между страницами.

## 6. Карточки объектов и редактирование

Создать единый механизм форм добавления и редактирования.

Требования:
- Обязательные поля визуально выделены.
- Поля проходят валидацию до записи в БД.
- Выпадающие списки используют централизованные справочники.
- При изменении объекта сохраняется история.
- При ошибке БД пользователь получает понятное сообщение.
- Успешные операции отображаются в интерфейсе.
- После сохранения связанные представления обновляются.
- При отмене редактирования данные не изменяются.
- Удаление опасных объектов требует подтверждения.

Нельзя допускать частично выполненных операций, оставляющих каталог в неконсистентном состоянии.

При изменении вложенных объектов учитывать внешние ключи и правила удаления.

## 7. Политики резервного копирования

Один из важнейших разделов приложения.

Система должна **учитывать настройки резервного копирования**, а не обязательно самостоятельно выполнять резервное копирование баз данных.

### 7.1. Уровни назначения

Политика резервного копирования может назначаться:

1. На весь экземпляр СУБД.
2. На конкретную базу данных.

При этом допускается существование политики уровня экземпляра и отдельных политик уровня БД в рамках одного экземпляра.

Например:

- Экземпляр PostgreSQL содержит пять баз данных.
- Для всех баз действует общая политика.
- Для одной критичной базы назначена отдельная политика.

Система должна корректно отображать такие ситуации.

**Важно:** отдельно определить правило эффективной политики: например, политика БД имеет приоритет над политикой экземпляра. В интерфейсе необходимо различать непосредственно назначенную и унаследованную политику.

### 7.2. Поля политики

Предусмотреть:
- Идентификатор политики.
- Название.
- Уровень назначения (экземпляр или БД).
- Ссылку на объект назначения.
- Тип резервного копирования.
- Планировщик / механизм выполнения.
- Расписание.
- Место хранения резервных копий.
- Срок хранения.
- Статус политики.
- Примечания.
- Даты создания и изменения.
- Авторов изменений.

Допускается расширение полей для конкретных технологий.

### 7.3. Статусы и неполные данные

Поддерживать статусы, включая **«Включен»** и **«Отключен»**.

Если политика отключена, отдельные параметры могут быть не заполнены.

Для неизвестных значений типа резервного копирования и планировщика предусмотреть значение **«Не указано»**.

Для активной политики должны действовать более строгие правила заполнения.

### 7.4. История политик

Все значимые изменения политики должны фиксироваться.

Пользователь с соответствующими правами может просмотреть:
- Что изменилось.
- Предыдущее значение.
- Новое значение.
- Кто внёс изменение.
- Когда это произошло.

Историю следует хранить отдельно от текущего состояния политики.

## 8. Пользователи, регистрация и авторизация

### 8.1. Первый запуск

При первом развёртывании системы должен существовать сценарий создания первоначального администратора.

Необходимо исключить возможность повторного несанкционированного создания первоначального администратора.

### 8.2. Авторизация

Пользователь входит по логину и паролю.

Требования:
- Пароли пользователей хранить только в виде защищённых хешей.
- Использовать современный алгоритм, например Argon2id.
- Не показывать пароли в журналах и сообщениях об ошибках.
- Реализовать понятную обработку неправильного логина или пароля.
- Обеспечить безопасную работу нескольких пользователей.

### 8.3. Регистрация

Предусмотреть регистрацию нового пользователя с последующим подтверждением администратором.

Возможные состояния учётной записи:
- Ожидает подтверждения.
- Активна.
- Заблокирована.
- Отключена.

До подтверждения пользователь не должен получать обычный доступ к каталогу.

### 8.4. Роли

Минимально предусмотреть:
- **Администратор** — полное управление приложением, пользователями, настройками и объектами.
- **Редактор** — создание и изменение разрешённых объектов.
- **Наблюдатель** — просмотр доступных разделов без изменения данных.

Права должны проверяться не только в интерфейсе, но и на уровне операций с данными.

Архитектура должна позволять расширять роли и разрешения.

### 8.5. Управление пользователями

Администратор должен иметь возможность:
- Просматривать пользователей.
- Подтверждать регистрации.
- Назначать роли.
- Блокировать и разблокировать учётные записи.
- Изменять разрешённые параметры.
- Просматривать связанные события аудита.

## 9. История изменений объектов

Для серверов, экземпляров СУБД, баз данных и политик РК необходимо сохранять историю изменений.

Каждая запись истории должна содержать:
- Тип объекта.
- Идентификатор объекта.
- Тип действия: создание, изменение, удаление, восстановление.
- Дату и время.
- Пользователя.
- Предыдущее состояние.
- Новое состояние.
- Перечень изменённых полей.

Историю нужно отображать в удобном виде: не просто JSON, а понятные пользователю названия полей и значения «Было / Стало».

### Восстановление

Администратор должен иметь возможность восстановить допустимое предыдущее состояние объекта.

При восстановлении:
- Проверять существование родительских объектов.
- Учитывать ограничения БД.
- Не терять более позднюю историю.
- Записывать сам факт восстановления как новое событие.
- Запрашивать подтверждение.

## 10. Журнал аудита

История объектов и аудит — разные механизмы.

**История** отвечает на вопрос: «Как менялся конкретный объект?»

**Аудит** отвечает на вопрос: «Какие действия совершали пользователи в системе?»

В журнал аудита включать:
- Входы и неудачные попытки входа.
- Выходы из системы, если событие отслеживается.
- Создание, изменение, удаление и восстановление объектов.
- Импорт и экспорт данных.
- Изменение пользователей и ролей.
- Изменение важных настроек.
- Массовое удаление данных.
- Другие критичные операции.

Предусмотреть:
- Фильтры по пользователю, действию, дате, объекту.
- Постраничную загрузку.
- Подробную карточку события.
- Защиту от изменения записей обычными пользователями.
- Ограничение доступа по ролям.

Не записывать в аудит пароли и другие секреты.

## 11. Уведомления

В системе должен быть отдельный раздел уведомлений.

Типичные события:
- Регистрация пользователя ожидает подтверждения.
- Пользователю предоставлены права.
- Изменились важные объекты.
- Произошло административное событие, требующее внимания.

Предусмотреть:
- Список уведомлений.
- Прочитанные и непрочитанные уведомления.
- Счётчик непрочитанных.
- Переход к связанному объекту или разделу.
- Корректное отображение времени события.

Набор событий должен быть расширяемым.

---

## 12. Избранное

Каждый пользователь может сохранять интересующие его объекты в персональном избранном.

Поддерживать:
- Серверы.
- Экземпляры СУБД.
- Базы данных.

Избранное одного пользователя не должно автоматически попадать в избранное другого.

Нужны добавление, удаление, просмотр списка и быстрый переход к объекту.

Если объект удалён, интерфейс должен корректно обрабатывать устаревшую ссылку.

## 13. Импорт Excel

Импорт должен поддерживать **два формата**.

### 13.1. Формат №1 — основной каталог

Исторический формат реестра содержит **21 колонку**.

Он используется для загрузки серверов, экземпляров СУБД, баз данных и связанных атрибутов.

При импорте:
- Читать Excel.
- Проверять структуру колонок.
- Нормализовать значения.
- Обнаруживать потенциальные дубли.
- Формировать иерархию объектов.
- Предлагать предварительный просмотр.
- Показывать ошибки до записи.
- Сохранять данные транзакционно.
- Формировать итоговый отчёт.

**Точные названия и порядок 21 колонки необходимо зафиксировать по исходному шаблону Excel. Нельзя придумывать их при реализации.**

### 13.2. Формат №2 — каталог с резервным копированием

Расширенный формат содержит **28 колонок**:

- Первые 21 колонка — данные основного каталога.
- Дополнительные 7 колонок — сведения о резервном копировании.

При импорте система должна создавать не только объекты каталога, но и связанные политики РК.

### 13.3. Определение уровня политики

В Excel сведения о резервном копировании могут повторяться в строках нескольких баз одного экземпляра.

Система должна анализировать строки, сгруппированные **по реальному экземпляру СУБД**, а не только по серверу.

Предусмотреть автоматическое предположение:
- Одна политика для всего экземпляра.
- Индивидуальные политики для отдельных баз.
- Смешанный вариант.

В окне предварительного просмотра пользователь должен иметь возможность исправить автоматически выбранный уровень.

Неоднозначные случаи, особенно когда в экземпляре всего одна база, нужно явно обозначать.

### 13.4. Пустые поля РК

Если все семь дополнительных колонок резервного копирования пусты, импортируется **только объект каталога**, без создания фиктивной политики.

Если политика указана, но статус отсутствует, допустимо использовать статус по умолчанию **«Отключен»**.

Для отключённых политик допустимы неполные сведения.

### 13.5. Защита от некорректного импорта

Предусмотреть:
- Проверку обязательных полей.
- Отчёт об ошибках по строкам.
- Предпросмотр количества новых и обновляемых объектов.
- Обработку повторяющихся записей.
- Подтверждение перед применением.
- Транзакционность.
- Отчёт об итогах.
- Запись операции в аудит.

Не допускать молчаливой потери данных.

## 14. Экспорт Excel

Экспорт должен создавать единый структурированный файл Excel.

### 14.1. Основной формат

Поддерживать экспорт **21 колонки**, совместимый с исходным реестром.

Основной принцип: **одна строка Excel соответствует одной базе данных**, а информация о сервере и экземпляре повторяется или группируется в соответствии с форматом шаблона.

Оформление:
- Читаемые заголовки.
- Выделение групп серверов и экземпляров.
- Границы и выравнивание.
- Разумная ширина колонок.
- Удобство фильтрации и печати.

### 14.2. Статистика при экспорте

Важно различать:
- Количество уникальных серверов.
- Количество записей «сервер / IP-адрес».
- Количество экземпляров СУБД.
- Количество баз данных.

Уникальность сервера не должна определяться простым количеством строк Excel.

Для сопоставления имён можно использовать нормализацию пробелов и регистра, например `lower(trim(name))`, но итоговое правило должно быть документировано.

## 15. Статистика

- Количество серверов.
- Количество экземпляров СУБД.
- Количество баз данных.
- Распределение по типам СУБД.

Статистика должна рассчитываться по данным PostgreSQL, а не по локальным копиям.

Для больших каталогов использовать эффективные SQL-запросы.

Предусмотреть переход от сводного показателя к соответствующим объектам, где это уместно.

## 18. Подключение к PostgreSQL

### 18.1. Принцип работы

Приложение подключается к центральному серверу PostgreSQL.

Параметры:
- Host.
- Port.
- Database.
- Username.
- Password.
- SSL mode.
- Имя схемы PostgreSQL (`dbcatalog` по умолчанию).
- Путь к корневому сертификату TLS при необходимости.

При необходимости архитектура должна поддерживать дополнительные параметры соединения.

### 18.2. Хранение параметров

Для Windows использовать:

`%LOCALAPPDATA%\DBCatalog\connection.json`

В JSON хранить только несекретные параметры.

Пароль подключения сохранять отдельно в Windows Credential Manager через Go-адаптер `go-keyring`. Не передавать сохранённый пароль из Go в интерфейс; интерфейс получает только состояние наличия реквизитов.

Не хранить пароль подключения в открытом виде:
- В исходном коде.
- В установщике.
- В файле JSON.
- В командной строке.
- В журналах.

### 18.3. Проверка подключения

Нужно отдельное окно настройки и проверки соединения.

Возможности:
- Ввод реквизитов.
- Проверка доступности сервера.
- Проверка авторизации PostgreSQL.
- Сообщение о конкретной категории ошибки.
- Сохранение только после успешной проверки либо явно подтверждённого действия пользователя.
- Возможность изменить подключение позднее.

При отсутствии PostgreSQL приложение не должно аварийно завершаться; показывать понятное сообщение без stack trace, DSN и секретов.

### 18.4. Схема данных

Использовать отдельную схему PostgreSQL, указанную в настройках подключения. По умолчанию — `dbcatalog`; пустое значение также означает `dbcatalog`. Смена схемы открывает отдельный каталог и не переносит данные между схемами.

При подключении автоматически создавать выбранную схему и применять ожидающие миграции до открытия каталога. База данных PostgreSQL должна существовать заранее. Все запросы, включая пользователей, аудит и историю, должны использовать выбранную схему. Журнал миграций хранить внутри неё. Конкурирующие клиенты синхронизировать advisory lock; при сбое откатывать всю транзакцию. Проверять контрольные суммы и отклонять неизвестные более новые версии. Не выполнять автоматический downgrade.

Для изменений структуры БД использовать последовательные версионированные миграции.

Миграции не должны уничтожать пользовательские данные при обычном обновлении приложения.

## 20. Требования к архитектуре кода

Проект необходимо **разработать с нуля**, не копируя механически структуру старого приложения.

Основные принципы:
- Разделение ответственности.
- Модульность.
- Статическая типизация Go, явные зависимости и небольшие интерфейсы на границах слоёв.
- Отсутствие циклических импортов пакетов; направление зависимостей от адаптеров к бизнес-логике.
- Независимость бизнес-логики от Wails, React и Windows API.
- Отсутствие SQL непосредственно в обработчиках кнопок.
- Повторное использование общих компонентов.
- Удобство тестирования.
- Предсказуемые ошибки.
- Простота добавления новых разделов.

Предлагаемая структура:

```text
CatalogDB/
├── go.mod
├── go.sum
├── main.go                   # точка входа Wails, сборка зависимостей
├── app.go                    # тонкий адаптер методов Go для интерфейса
├── wails.json
├── README.md
├── .gitignore
├── internal/
│   ├── config/               # настройки, несекретные параметры подключения
│   ├── domain/               # сущности, правила, инварианты
│   ├── application/          # сценарии, DTO, права, транзакции, интерфейсы портов
│   ├── infrastructure/
│   │   ├── postgres/         # pgxpool, репозитории, реализация транзакций
│   │   ├── migrations/       # версионированные SQL-миграции, go:embed
│   │   ├── security/         # Argon2id, сессия, Credential Manager
│   │   ├── excel/            # Excelize, адаптеры двух форматов
│   │   └── filestore/        # выбранный механизм хранения файлов
│   └── presentation/         # привязки Wails, преобразование ошибок, события
├── frontend/
│   ├── package.json
│   ├── package-lock.json
│   ├── src/
│   │   ├── components/
│   │   ├── pages/
│   │   ├── styles/
│   │   └── types/
│   └── wailsjs/              # генерируемые привязки Go/TypeScript
├── build/                    # ресурсы Windows и выходные файлы Wails
├── tests/
│   ├── integration/
│   └── ui/
├── packaging/
│   ├── inno_setup/
│   └── build.ps1
└── docs/
```

Модульные тесты Go размещать рядом с соответствующими пакетами в файлах `*_test.go`. Структура показывает назначение каталогов, а не требует создавать пустые пакеты. `main.go` должен находиться в корне проекта Wails; инфраструктурные адаптеры не должны попадать в доменный слой.

Это рекомендуемая структура, которую можно адаптировать при проектировании.

### 20.1. Слои

**Domain:** сущности, бизнес-правила, инварианты.

**Application:** сценарии использования, управление транзакциями, проверка разрешений.

**Infrastructure:** PostgreSQL, репозитории, Excel, хранение настроек и интеграции.

**Presentation:** React-компоненты, окна и диалоги, модели представления и тонкие адаптеры Wails. UI вызывает сценарии через ограниченный набор методов Go, а не выполняет SQL.

Нельзя допускать, чтобы изменение оформления кнопки требовало изменения SQL-запросов или бизнес-логики.

### 20.1.1. Граница Go и интерфейса

- Проверять права и входные данные в Go при каждом вызове сценария; скрытая кнопка не является проверкой доступа.
- Не предоставлять интерфейсу универсальные методы выполнения SQL, чтения произвольных файлов или извлечения секретов.
- Не передавать пароль PostgreSQL, хеши паролей пользователей и внутренние реквизиты через DTO или события Wails.
- Пользовательский пароль принимать только для выполнения соответствующей операции, не сохранять в состоянии интерфейса и журналах.
- Длительные операции выполнять без блокировки интерфейса; использовать `context.Context`, тайм-ауты, отмену и события прогресса с идентификатором операции.
- Не создавать неограниченное число goroutine и соединений. Изменения интерфейса выполнять средствами React, не обращаться к DOM из фоновых задач Go.
- Загружать интерфейс из локальных ресурсов; не разрешать выполнение удалённого содержимого в контексте с доступом к привязкам Go. Предусмотреть Content Security Policy и безопасную обработку внешних ссылок.
- Даты передавать в согласованном формате с часовым поясом. Идентификаторы PostgreSQL `bigint` передавать строками либо использовать UUID, чтобы исключить потерю точности JavaScript.

### 20.2. Размер модулей

Не создавать огромные файлы на 1000–2000 строк, в которых смешаны разные обязанности.

При этом не дробить проект искусственно до одного метода на файл.

Один модуль должен решать понятную задачу.

```text
build/

    └── CatalogDB.exe
```

`packaging/build.ps1` должен проверять версии инструментов и выполнение сборки интерфейса, Go-тестов и release-сборки, затем вызывать Inno Setup. Не хранить пароли или локальные настройки подключения в ресурсах EXE.

На компьютере пользователя не требуются Go, Node.js и инструменты разработки. Требуется WebView2 Runtime: установщик проверяет его наличие и использует официальный подписанный установщик Microsoft. Для закрытой сети предусмотреть согласованный офлайн-дистрибутив WebView2. Поддерживаемые версии Windows и архитектуры явно зафиксировать после проверки совместимости; ARM64 не считать поддержанным без отдельной сборки и тестирования.

Linux-среда может использоваться для независимых Go-пакетов и проверок интерфейса. Успешные Linux-проверки не подтверждают работу Windows Credential Manager, окон Wails, DPI, установщика или Windows EXE. Финальные проверки проводить на Windows; возможность кросс-компиляции не считать заменой этим проверкам.

## 29. Решения, которые необходимо уточнить перед реализацией

### 29.1. Доверенная граница и права доступа

Исходное требование прямого подключения настольных клиентов к PostgreSQL сохранено. Однако проверки ролей только в Go-клиенте не защищают от пользователя, который получил общую учётную запись PostgreSQL и обращается к данным напрямую. Windows Credential Manager защищает хранение реквизитов, но не превращает настольный клиент в доверенный сервер.

До реализации ролевой модели выбрать и документировать один из вариантов:
- Сохранить прямое подключение и обеспечить ограничения на стороне PostgreSQL: отдельные идентичности и роли, ограниченные привилегии, защищённые функции и/или RLS, защита истории и аудита. Отдельно спроектировать безопасную регистрацию, вход и первоначальное создание администратора. Нельзя передавать всем клиентам общую роль с неограниченным доступом к таблицам.
- Вынести авторизацию, бизнес-операции и доступ к PostgreSQL в центральный API на Go. Настольный клиент обращается к API; реквизиты PostgreSQL остаются на сервере. Это изменение исходной архитектуры: потребуются отдельный сервис, TLS, развёртывание и изменение окна настройки подключения. Применять только как явно согласованное изменение ТЗ.

Миграции и начальное развёртывание выполнять с отдельными административными полномочиями; обычный клиент не должен постоянно иметь DDL-права. Согласовать единственного исполнителя миграций и блокировку конкурирующего запуска при обновлении нескольких клиентов.

### 29.2. Входные материалы и бизнес-правила

- Получить исходные Excel-шаблоны на 21 и 28 колонок; точные заголовки, типы данных и правила сопоставления не определять по догадке.
- Утвердить правило эффективной политики РК, включая отключённую политику БД, несколько политик и отсутствие политики. Приоритет политики БД указан как рекомендуемый вариант и ожидается в тестах, но поведение пограничных случаев требует фиксации.
- Определить ключи идентификации серверов и реальных экземпляров СУБД, включая Oracle, правила дублей и повторного импорта.
- Выбрать физическое хранилище файлов, права доступа, резервное копирование и поведение при недоступности хранилища; метаданные и файлы могут требовать согласования при частичном сбое.
- Утвердить состав массового удаления и правила обработки истории, связанных объектов и восстановления.

Эти уточнения не отменяют остальные функциональные требования. Документ описывает целевой проект; приведённые команды сборки и тестирования должны быть реализованы и проверены после создания кода приложения.


## 30. Уточнения версии 0.3.0

- Символ `|` в поиске означает «И». Все непустые части должны встречаться в значениях одной иерархической цепочки «сервер → экземпляр → БД»; совпадения из разных соседних БД не объединяются. Регистр не учитывается, фрагменты трактуются буквально.
- Удаление родителя удаляет его дочерние записи и политики РК в одной транзакции с сохранением истории и аудита каждого объекта. Перед подтверждением показывается состав; изменения состава или версий требуют повторного подтверждения.
- В настройках доступна административная очистка всего каталога с двумя последовательными подтверждениями. Пользователи, справочники, настройки, история и аудит не удаляются.
- Среда эксплуатации и состояние отображаются в карточке цветными метками с текстом; другие значения справочников и множественный выбор оформляются согласованно. Раздел Excel называется «Экспорт/Импорт».
