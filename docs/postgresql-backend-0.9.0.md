# PostgreSQL backend, живые обновления и сохранённый вход — 0.9.0

## Обновление

Сначала сделайте обычную резервную копию рабочей БД и закройте старые клиенты. Запустите 0.9.0 и подключитесь к нужной схеме: автоматически применяются миграции 010–016 в одной транзакции. Не изменяйте файлы 001–009 и их контрольные суммы.

Перенос таблиц требует блокировок и свободного места для новых таблиц/индексов и WAL. Бюджет подключения/миграций увеличен до 10 минут. Это не обещание обновления без паузы записи на большой рабочей базе. Старая версия после обновления отклоняется журналом миграций; дополнительно блокируются записи уже подключённого старого desktop-клиента. Маркер протокола — механизм совместимости, не авторизация.

Отдельный вариант для администратора, **вместо автоматического первого обновления**:

~~~bash
psql -X -h HOST -U USER -d DATABASE -v catalog_schema=YOUR_SCHEMA -f CatalogDB-upgrade-009-to-016.sql
~~~

[Файл перехода](../downloads/CatalogDB-upgrade-009-to-016.sql) · [SHA-256](../downloads/CatalogDB-upgrade-009-to-016.sql.sha256).

Файл рассчитан на существующую схему с миграциями 001–009; проверяет известные контрольные суммы, отсутствие пропусков и более новых версий, берёт тот же advisory lock, обновляет журнал и фиксирует все шаги вместе. Повторный запуск проверяет журнал и пропускает применённые шаги. При ошибке транзакция откатывается. Это psql-сценарий с метакомандами, не файл для произвольного SQL-редактора. Если параметр схемы не задан, используется dbcatalog. Файл воспроизводимо создаётся командой python3 packaging/export-migration-bundle.py.

Расширение pg_trgm устанавливается, если оно доступно и разрешено текущей PostgreSQL-роли; иначе поиск остаётся корректным без триграммного индекса. Самостоятельно сервер не перезапускается, pg_stat_statements/pg_cron/pg_partman не устанавливаются. При восстановлении только выбранной схемы на другой сервер расширение pg_trgm может потребовать отдельной предварительной установки: оно находится вне прикладной схемы.

## Миграции и объекты

| Миграция | Содержание |
| --- | --- |
| 010 | Общие VIEW контекста/объектов, SQL API страниц и глобального поиска, локальные поисковые документы, GIN при pg_trgm, индексы родителей/фильтров/избранного, расширенная статистика |
| 011 | Месячные UTC-секции audit_events, DEFAULT, функция maintain_catalog_partitions, перенос старых событий с проверкой |
| 012 | SQL API сохранения, удаления и восстановления; триггеры технических полей/истории/перемещений; HASH-секции версий/событий; совместимые object_history и совместное использование состояний |
| 013 | Формирование уведомлений в PostgreSQL и сигналы NOTIFY после фиксации |
| 014 | Сохранённые сессии с хешем токена, сроком, отзывом и автоматическим отзывом при смене пароля/блокировке |
| 015 | COPY/staging импорта, пакетная правка, серверные функции статистики/качества/подсказок |
| 016 | Предпросмотр/подтверждение перемещений в БД, проверки и защита от старого протокола клиента |

Пути и эффективная политика централизованы; отключённая собственная политика БД по-прежнему перекрывает наследуемую. Oracle SID остаётся непосредственно на сервере. SID уникален в рамках своего родителя, не глобально. Адрес сервера остаётся текстом, допустимы DNS-имена.

Обычная ветка читается без общего поискового CTE. Поиск, счётчики и выбранные строки страницы считаются сервером в одной SQL-команде. Сохраняются AND через «|», Unicode, буквальные %/_, отсутствие склейки совпадений соседних БД, поиск/выбор/экспорт за пределами загруженных страниц. Триграммный отбор используется для термов без пробелов, затем выполняется точная проверка всей цепочки; запросы с пробелами корректны, но могут требовать полного просмотра. Поисковый документ хранится один на объект, без размножения инструкции сервера по всем дочерним БД.

## История и секции

audit_events делится на месяцы created_at по UTC, ключ (created_at,id), общая последовательность ID. Подготовлены месяцы имеющихся событий и текущий/три следующих. Неожиданные даты принимаются DEFAULT-секцией. При подключении приложение вызывает maintain_catalog_partitions; функция под блокировкой переносит записи DEFAULT в нужные секции и безопасна при повторном вызове. Автоматического удаления истории нет.

history_events и record_versions разделены на 8 HASH-секций по (entity,object_id). Частые запросы истории/версий содержат эти ключи. Структура не обещает ускорения всех запросов; основные выгоды — локальные индексы и обслуживание большого хранилища.

Полное состояние версии хранится в record_versions; события обычно ссылаются на версии до/после. Если старое состояние отличается от канонической версии или не имеет версии, оно сохраняется как отдельное fallback-значение. object_history остаётся совместимым представлением с полными before_state/after_state. Внешние ключи защищают ссылки событий, UPDATE/DELETE сохранённых версий блокируются триггером. Возврат создаёт новую версию.

Технические поля, история, аудит и перемещения фиксируются триггерами даже при прямом разрешённом SQL. Для корректного прикладного автора административной SQL-операции задайте SET LOCAL catalogdb.actor_id внутри транзакции; без него используется updated_by записи. Контекст не заменяет доверенную авторизацию: обладатель общих прямых реквизитов БД может его подставить.

Удаление архивируется перед FK-каскадами избранного. Восстановление проверяет родителей/конфликты и получает следующий номер версии. Вложения сохраняют связь с UUID. Подтверждение восстановления отслеживает относящиеся к нему записи, родителей и конфликты имён вместо любых посторонних изменений каталога.

## Импорт и блокировки

Excel по-прежнему разбирается в Go, пользователь исправляет/исключает строки и подтверждает политики. Текущее состояние читается по относящимся к книге серверам, экземплярам и именам БД. Подготовленные операции загружаются COPY во временную таблицу, применяются сервером в порядке зависимостей через общий API записи. Внутри PostgreSQL остаётся последовательная проверка отдельных операций; это не обещание полностью наборного INSERT для всех форматов.

Массовая правка использует один UPDATE FROM и блокирует выбранные БД в стабильном порядке. Для импорта, дерева удаления, восстановления и перемещения сохранены более широкие блокировки, защищающие прежние гарантии предпросмотра. Механически снимать их без нового протокола конкурентной записи нельзя.

## LISTEN/NOTIFY

Существующий процесс CatalogDB открывает отдельное соединение LISTEN с теми же TLS-настройками. Дополнительной службы нет.

Сигнал содержит только схему и тип изменения, без паролей/файлов/полного состояния. PostgreSQL доставляет его после COMMIT и объединяет одинаковые сигналы одной транзакции. Интерфейс объединяет события, обновляет нужные данные, сохраняет открытые формы и предупреждает об изменении каталога. При сохранении остаётся проверка версии.

Слушатель переподключается с задержкой до 30 секунд и инициирует resync. После возвращения окна и раз в минуту выполняется контрольная синхронизация, включая проверку срока входа и роли. При ошибках есть задержка повторных попыток. Ответы старой сессии отбрасываются. NOTIFY не является надёжной очередью; таблица notifications и фактические записи остаются источником данных.

## Сохранение входа

В форме входа укажите «Сохранить вход на (часов)»: 0 — без сохранения, целое число 1–168 — запомнить вход на этом компьютере.

Пароль пользователя остаётся только для обычной проверки Argon2id. Случайный токен хранится в системном хранилище, в PostgreSQL — SHA-256 токена и срок. Он привязан к конкретному подключению/схеме; срок при перезапуске не продлевается. В connection.json и localStorage пароль/токен не записываются.

Для входа без ручного подключения также должно быть настроено сохранение реквизитов соединения PostgreSQL. Если соединение не сохранено, сначала подключитесь — прикладная сессия затем восстановится.

Закрытие приложения сохраняет токен до срока. «Выйти», смена пароля и блокировка отзывают сохранённый вход. Каждая операция проверяет актуальность роли, состояния и токена; роль после восстановления не берётся из старого кеша. Повреждённая/просроченная запись возвращает к обычному входу. Если системное хранилище не позволяет записать токен, сохранение входа завершается ошибкой без действующего неперсистированного токена; можно войти с 0 часов.

Сеанс без сохранения по-прежнему живёт в памяти процесса. Смена пароля отзывает сохранённые токены; роль/блокировка проверяются для всех сеансов.

## Границы переноса

Go сохраняет файлы/XLS/XLSX/DOCX, Windows-интеграцию, Argon2id, управление сессией, раннюю валидацию и координацию подтверждений. Создание PostgreSQL-ролей и серверная настройка pg_stat_statements остаются задачами администратора БД; текущий общий доступ native-клиентов не превращён в изолированные PostgreSQL-идентичности пользователей.

EXE не обязательно станет меньше: миграции встроены в него вместе с Wails, Go runtime и Excel-библиотеками. Оценивать нужно отдельно скорость SQL/сетевые запросы, размер БД и размер поставки.

Тесты, измерения и ограничения Windows: [validation-0.9.0.md](validation-0.9.0.md).
