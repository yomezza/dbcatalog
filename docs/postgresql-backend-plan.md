# План переноса логики CatalogDB в PostgreSQL 17

Статус обновлён: основной перенос реализован в 0.9.0, схема 016. Ниже сохранён исходный план; фактическая реализация и границы описаны в [postgresql-backend-0.9.0.md](postgresql-backend-0.9.0.md).

Реализованы представления/серверный поиск и страницы, индексы, запись/история/версии, переносы, пакетное архивирование/восстановление, COPY импорта, пакетная правка, секции/обслуживание, совместное хранение состояний, серверные уведомления/LISTEN и отчётные функции. Добавлены сохранённые сессии с ограниченным сроком.

Не включались автоматически: создание PostgreSQL-ролей, перезапуск сервера ради pg_stat_statements, pg_cron/pg_partman и удаление старых секций. Глобальные блокировки сохранены для импорта, удаления, восстановления и переноса ради существующих гарантий предпросмотра; массовая правка переведена на блокировки выбранных строк. Имена, роли, валидация Excel и пользовательские подтверждения частично остаются в Go как координация и ранняя проверка.

## Что исследовано

Миграции 001–009; ограничения/индексы; пул и права; чтение каталога/поиск/фильтры/выбор/экспорт; запись объектов/политик; импорт; массовая правка; архив удаления/восстановление; история/версии/перемещения; вложения; аудит/уведомления/статистика/качество.

Повторная проверка показала:
- Предпросмотры удаления/переноса и подтверждения зависят от текущих правил блокировки. Механическое удаление LOCK TABLE нарушит гарантии.
- Восстановление удалённых записей строит подтверждение по версиям всего каталога, поэтому посторонняя правка может отменить предпросмотр.
- Разные разделы повторяют соединения родителей и выбор эффективной политики.
- object_history хранит before/after; record_versions ещё раз хранит состояние версии. Это отдельная задача оптимизации хранения.
- Триггер capture_record_version висит на object_history, не на основных таблицах: прямой UPDATE объекта пока обходит историю.
- Журнал аудита дополнительно ищет последнее имя объекта в истории. Можно сохранять имя на момент события, сократив этот поиск и сделав смысл аудита точнее.
- Поиск выполняет несколько отдельных запросов с повторным MATERIALIZED CTE; materialization не переиспользуется между SQL-командами.
- Адрес сервера может быть DNS-именем: перевод всего поля address в inet недопустим.
- SID уникален внутри своего родителя, а не во всём каталоге. Это правило сохраняется.

## Секционирование: конкретное решение

### Аудит

Предварительный выбор — месячные RANGE-секции created_at по UTC. Приложение уже поддерживает фильтр периода. Такой фильтр позволит исключить ненужные месяцы. Просмотр всех событий без периода всё равно читает несколько секций; ускорение любого запроса не гарантируется.

В PostgreSQL 17 уникальный ключ секционированной таблицы должен включать ключ секционирования. Нельзя сохранить текущий PRIMARY KEY(id) без пересмотра. План: PRIMARY KEY(created_at,id), общая последовательность ID, запрет прикладного назначения ID через контракт записи. Если обнаружатся требования к формально глобальной уникальности id независимо от даты, понадобится отдельный реестр идентификаторов, а не обещание уникальности одной последовательностью. Сейчас межтабличных FK на audit_events.id нет; существующие данные и API всё равно проверяются.

Готовятся секции текущего и трёх следующих месяцев и DEFAULT-секция на случай пропущенного обслуживания/нетипичной даты. DEFAULT — страховка, не постоянное место хранения. Перенос её записей и присоединение новых секций выполняются явно, с учётом блокировок и проверки диапазонов.

Автоматического удаления/отсоединения старых месяцев в первом выпуске не будет. Это поменяло бы доступность истории и требует отдельно согласованного срока хранения.

### История и версии

Частые запросы содержат entity/object_id, но не период. Поэтому месяцы могут увеличивать число просматриваемых секций. Сначала сравниваются обычная таблица и HASH(entity,object_id), 8 секций; число фиксируется по результатам теста.

PRIMARY KEY record_versions(entity,object_id,version) совместим с таким HASH-ключом. Для object_history потребуется пересмотреть PRIMARY KEY(id), например на (entity,object_id,id), и проверить все обращения по ID. Существующий RestoreObject дополнительно передаёт entity/object_id. Триггер версий, локальные индексы, последовательность и обработка исторических данных должны быть сохранены.

Сам каталог серверов/экземпляров/БД, справочники и users пока не секционируются. Это не уменьшает число строк результата и на нынешних объёмах может только усложнить схему.

### Кто обслуживает секции

В ядре PostgreSQL 17 нет встроенного календарного планировщика заданий. pg_cron и pg_partman не являются частью обязательного ядра и в текущей тестовой среде не установлены. План от них не зависит.

Функцию обслуживания вызывает существующее приложение в контролируемом административном сценарии/при подготовке подключения, а не триггер каждой вставки. DEFAULT обеспечивает приём записей до следующего обслуживания. Периодический вызов через уже имеющийся планировщик организации — опция, не новая Go-служба. Права на DDL ограничиваются; динамические имена принимаются только из проверенных внутренних правил. Пользовательский текст не становится SQL.

## Что ещё можно перенести, а что оставляем

В PostgreSQL выгодно держать операции над связями и наборами: эффективные политики, проверки целостности, технические версии, архивирование, историю, назначения, пакетную запись и серверный поиск. Одна функция здесь заменяет несколько запросов через сеть.

В Go остаются Wails/WebView2 bridge, файлы/системные диалоги, XLS/XLSX и DOCX, Windows Credential Manager, запуск RDP/SSH, TLS, жизненный цикл сессии и пользовательские подтверждения. Argon2id остаётся в Go: pgcrypto не предоставляет прямую замену используемому алгоритму, а менять его на другой ради уменьшения приложения не планируется.

SECURITY DEFINER не включается у всех функций автоматически: это увеличивает полномочия и может мешать встраиванию SQL-функций планировщиком. Для необходимых привилегированных операций нужны фиксированный безопасный search_path, квалифицированные имена объектов и ограниченный EXECUTE. Прикладной actor_id из SET LOCAL сам по себе не удостоверяет личность: клиент с теми же прямыми правами БД может его подставить. Роли PostgreSQL, доверие к клиенту и проверка прикладной сессии рассматриваются вместе.

Обычный VIEW не кеширует результат. STABLE SQL-функция не означает «один расчёт на транзакцию». MATERIALIZED CTE живёт в одной SQL-команде. Materialized view требует явного обновления; актуальность каталога и поиска нельзя незаметно заменить отложенным кешем.

## Размер EXE

Перенос бизнес-логики упростит Go и уменьшит число сетевых запросов, но существенное уменьшение EXE пока не обещается. В сборке остаются Go runtime, Wails/WebView2, PostgreSQL-драйвер, Excel-библиотеки и интерфейс. SQL миграций встроен в EXE через go:embed — новая серверная логика тоже входит в поставку. После каждого этапа отдельно измеряются EXE/ZIP, время операций и объём БД.

## Измерения и проверки

Предыдущая проверка текущего SQL: PostgreSQL 17.11, 100 серверов, 500 экземпляров, 100 000 синтетических БД, без политик/вложений, ANALYZE, jit=off, EXPLAIN (ANALYZE,BUFFERS), тёплый кеш. Временная схема полностью откатилась.

| Отдельный запрос | Время, мс |
| --- | ---: |
| Общие счётчики без фильтров | 152,990 |
| Общие счётчики с поиском SID | 307,072 |
| Страница БД одной ветки текущим запросом | 121,988 |
| Прямая страница той же ветки без поисковых фильтров | 0,599 |
| Общие количества проблем качества | 891,023 |

Прямая выборка показывает цену общего пути, а не полную замену поиска. Время одного SQL не равно времени экрана. Это разовые измерения в облачной среде, не производственный SLA.

Для новых этапов: одинаковые данные до/после; 100 000 БД и отдельный большой набор событий с датами за несколько лет; Oracle/обычные БД, политика отсутствует/отключена/унаследована; несколько конкурентных клиентов; изменение роли; stale preview; ROLLBACK; короткий/Unicode/многотермовый поиск; полная история и возврат версии; установка в пользовательскую схему; восстановление резервной копии.

Все изменения — новыми миграциями после 009, без правки контрольных сумм применённых миграций. Перенос больших таблиц проверяет количество/ключи и доступность истории; сохраняет последовательности, триггеры, индексы и права. CREATE INDEX CONCURRENTLY не запускается внутри текущей атомарной миграции: при необходимости понадобится отдельная отслеживаемая стадия обслуживания.

Политика: сначала этап A с измеряемым выигрышем, затем единая запись/история B, после этого секции C и сокращение хранения/уведомлений D. Полная замена приложения набором произвольных SQL-функций не является целью; интерфейс получает небольшой определённый контракт операций.
