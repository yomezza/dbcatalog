# Инструкции для ассистента CatalogDB

## Начало работы

- Сначала прочитайте [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md). Затем — [разработку и проверки](docs/DEVELOPMENT.md), [известные ограничения](docs/KNOWN_ISSUES.md) и исходники затрагиваемой части.
- Это продолжение существующего проекта: сохраняйте решения и инварианты из контекста. Старое ТЗ и ранние разделы README могут описывать предыдущие версии; сверяйте их с актуальным кодом и дополнениями пользователя.
- Актуальный репозиторий — `yomezza/dbcatalog`, рабочая ветка на момент передачи — `catalogdb-go`. Историческое имя Go-модуля `github.com/yomezza/test` пока сохранено; не переименовывайте импорты механически.
- Пользователь предпочитает русский язык и короткие ответы. Выполняйте порученную работу до проверяемого результата; обсуждение или просьба «пока не реализовывай» не разрешают внедрять обсуждаемые идеи.
- Не задавайте заново вопросы, на которые уже есть ответы в контексте. Уточняйте существенные новые неоднозначности, а обычные обратимые решения принимайте самостоятельно.
- Не коммитьте пароли, токены, рабочие Excel, выгрузки и реальные данные каталога. Для тестов и иллюстраций используйте отдельные схемы и вымышленные записи.

## Инварианты

- Пользователь выбирает PostgreSQL-базу и схему; пустая схема означает `dbcatalog`. Смена схемы открывает другой каталог, не переносит данные.
- Не изменяйте применённые миграции `001`–`016`: проверяются SHA-256. Изменение БД оформляйте следующей миграцией.
- Oracle SID принадлежат непосредственно серверу; обычные БД — экземпляру. SID не уникален глобально.
- `|` в поиске означает логическое И в одной цепочке объектов. Поиск, фильтры и экспорт охватывают все данные, а не только загруженные страницы.
- Сохраняйте предпросмотр, повторную проверку прав/версий и атомарность массовых операций. Не снимайте блокировки без доказательства сохранности этих гарантий.
- LISTEN/NOTIFY уже реализован. Открытые формы пользователя нельзя молча перезаписывать чужими изменениями.
- Прямой PostgreSQL-доступ и прикладная роль — разные границы прав. Общие широкие реквизиты БД позволяют обходить проверки приложения; не обещайте обратного.
- Переход на персональные PostgreSQL-логины и PostgREST пока не реализованы и не поручены к внедрению.

## Правила выпуска

При выпуске каждой новой версии приложения обязательно публикуйте соответствующий GitHub Release в yomezza/dbcatalog. Это постоянное требование пользователя.

- Собирайте Windows x64 и Linux x64 из одной версии исходников; выполняйте подходящие проверки.
- Сохраняйте архивы и SHA-256 в downloads. Не заменяйте файлы уже опубликованных версий другим содержимым.
- Добавляйте версию в packaging/releases/manifest.json с описанием изменений, полным SHA коммита с архивами и всеми вложениями.
- Создавайте тег vVERSION на соответствующий коммит. При существующем теге не передавайте target_commitish в запрос создания Release.
- Запускайте python3 packaging/publish-releases.py для проверки. После push манифеста workflow Publish CatalogDB releases публикует выпуск через CATALOGDB_RELEASE_TOKEN.
- До сообщения об окончании выпуска проверяйте успешность публикации, публичную страницу Release и доступность всех файлов. Не ограничивайтесь файлами в downloads или артефактами Actions.
- Не считайте задачу выпуска завершённой, если публикация заблокирована; сообщите конкретную причину. Никогда не выводите токены в чат или исходники.
- **Новое требование пользователя для следующих выпусков:** Release label — предпочтительно **Latest**, иначе **None**; не копируйте прежний **Pre-release** по умолчанию. Исторические релизы без отдельной просьбы не перемаркировывайте.
- Автоматизация ещё не приведена к новому правилу: в манифесте опубликованные версии имеют `prerelease: true`, а publisher задаёт `make_latest: false`. Перед следующим выпуском предусмотрите выбор для нового релиза, сохранив настройки исторических. Не меняйте `make_latest` глобально: publisher обходит все версии.
- Изменения только документации и файлов контекста сами по себе не требуют новой версии приложения, пересборки или Release.

## Перед завершением работы

- Проведите проверки, соответствующие изменению; не считайте пропущенные интеграционные тесты проверкой PostgreSQL или кросс-сборку проверкой Windows GUI.
- Обновите контекст при изменении архитектуры, инвариантов, версии, требований пользователя или известных ограничений. Различайте реализованное, согласованное и только предложенное.
- Wiki находится в отдельном Git-репозитории: push основного кода не обновляет её. Порядок работы описан в DEVELOPMENT.md.
